## ١. الفكرة المعمارية في سطرين

التطبيق **غلاف أندرويد رقيق حول واجهة ويب مدمجة**. كل المنطق والواجهة في
`assets/` (HTML + JS خالص، بلا أُطر ولا حزم)، وجافا تقدّم ثلاثة أشياء لا
يقدر عليها WebView وحده: **قاعدة بيانات SQLite**، **مشاركة ملف حقيقي**،
و**الطباعة**.

```
┌──────────────── APK ────────────────┐
│  MainActivity (WebView)             │
│    ├─ NativeDb      ──→ DaliliDb ──→ dalili.db (SQLite)
│    └─ AndroidBridge ──→ PrintManager / ACTION_SEND
│                                     │
│  assets/index.html  ← الواجهة والأنماط
│  assets/app.js      ← كل المنطق
│  assets/library.js  ← المكتبة الجاهزة (بيانات ثابتة)
└─────────────────────────────────────┘
```

**بلا إنترنت إلا لغرضٍ واحد:** `INTERNET` في `AndroidManifest.xml` موجودة
منذ ٥٫٢ **لفحص وجود إصدار أحدث وحده** — طلب `GET` واحد لعنوانٍ ثابت
مكتوبٍ في `MainActivity.UPDATE_URL`، لا يحمل معه شيئًا ولا يأتي من
الواجهة. وما عدا ذلك القيد قائم كما كان:

- **لا ملف خارجي واحد** في الأصول: لا CDN ولا خطّ ولا سكربت. قيدٌ تصميمي.
- **الواجهة محبوسة في `assets`**: `WebViewClient` يرفض كل تنقّلٍ أو موردٍ
  ليس `file://` (`shouldOverrideUrlLoading` + `shouldInterceptRequest`).
  فلو أُقحم رابطٌ خارجي في الصفحة يومًا لم يُحمَّل.
- **لا بيانات تخرج**: لا قاعدة البيانات ولا شيء منها يمرّ بالشبكة، وفحص
  التحديث نفسه يُطفَأ من الإعدادات فلا يبقى أي اتصال.

## ٣. البناء

### أ) Android Studio (الأسهل)

1. **File ← Open** ← اختر مجلد المشروع
2. انتظر Gradle Sync
3. **Build ← Build App Bundle(s) / APK(s) ← Build APK(s)**
4. الناتج: `app/build/outputs/apk/debug/app-debug.apk`

### ب) سطر الأوامر

يحتاج JDK 17+ وAndroid SDK (platform 34، build-tools 34).

```bash
echo "sdk.dir=/path/to/Android/sdk" > local.properties
chmod +x gradlew
./gradlew assembleRelease          # أو assembleDebug
# الناتج: app/build/outputs/apk/release/app-release.apk
```

تثبيت مباشر على جهاز موصول:

```bash
./gradlew installRelease
# أو
adb install -r app/build/outputs/apk/release/app-release.apk
```

### ج) التوقيع

`buildTypes.release` يستخدم `signingConfigs.debug` عمدًا حتى يُثبَّت الملف
مباشرةً بلا إعداد. **للنشر الرسمي** أنشئ مفتاحك:

```gradle
signingConfigs {
    create("release") {
        storeFile file("my-key.jks")
        storePassword System.getenv("KS_PASS")
        keyAlias "dalili"
        keyPassword System.getenv("KEY_PASS")
    }
}
buildTypes { release { signingConfig signingConfigs.release } }
```

ولا تُدخل ملف المفتاح ولا كلمات السر في المستودع.

### د) رقم الإصدار

في `app/build.gradle`، وهو **المصدر الوحيد**: التطبيق يعرض رقمه في
«الإعدادات ← حول» قارئًا إياه من الحزمة المثبَّتة عبر
`AndroidBridge.appVersion()` (`PackageManager`)، لا من ثابت مكتوب في
`app.js`. فلا يوجد رقم ثانٍ يُنسى تحديثه ولا احتمال أن يخالف المعروضُ ما
ثبّته المستخدم فعلًا.

ارفع **الاثنين** مع كل إصدار توزّعه:

```gradle
versionCode 43       // رقم صحيح يزيد دائمًا — أندرويد يمنع التحديث بدونه
versionName "5.2"    // ما يراه المستخدم
```

### قواعد الأسلوب

- **ES5 صرف** (`var`, `function`) — WebView على أندرويد ٧ لا يضمن ما بعده.
  الاستثناءان: `async/await` في دوال الـPIN، وهما مدعومان منذ أندرويد ٨؛
  إن أردت دعم ٧ فعلًا استبدلهما بـPromises.
- **بلا حزم ولا أدوات بناء للواجهة.** لا npm، لا حزم، لا transpile.
- كل ما تناديه سمة `onclick` في HTML يجب أن يكون على `window` صراحةً:
  `window.medSave = function (id) { … }`
- **كل نص من المستخدم يمرّ بـ`esc()`** قبل وضعه في HTML. لا استثناء.
- الرسم عبر `h(id, html)` الذي يكتب `innerHTML` — أي إعادة رسم تُفقد حالة
  الحقول، لذا البحث والفتح/الطي يُدار بعناية (انظر §٩).

### الحالة العامة

```js
DB = {
  meds: [], labs: [], imaging: [], recipes: [],   // العناصر
  cart:   { meds: [], labs: [], imaging: [], recipes: [] },
  sections: [],                                   // {id,title,icon,builtin} — الأقسام
  fields:   [],                                   // {id,kind,key,label,type} — حقول المستخدم
  cats:   [],                                     // {id, kind, name} — التصنيفات
  groups: [],                                     // {id, kind, name, items[]}
  out:    { … },                                  // الحقول المرسلة لكل قسم
  header: { name: '', title: '', contact: '' },   // ترويسة الطباعة (اختيارية)
  backup_at: 0,                                   // آخر نسخة احتياطية
  pin_hash: null
}
```

`DB` هي نسخة الذاكرة من قاعدة البيانات. كل تعديل يكتب في **الاثنين**:
`DB` أولًا ثم `Store.*` — والواجهة تُرسم من `DB`.

## ٥. التنقّل

مكدّس بسيط:

```js
NAV = ['home']            // آخر عنصر هو الصفحة الحالية
goPage('labs')            // يدفع
goBack()                  // يسحب (مع حارس التعديلات غير المحفوظة)
goHome()                  // يعيد التهيئة
```

أسماء الصفحات: `home`, `meds`, `labs`, `imaging`, `recipes`, `settings`,
`secs`, `pv`, `lib:<kind>`, `cat:<kind>`, `fld:<kind>`, `grp:<kind>`,
`grp:<kind>:<groupId>`، ومعرّف أي قسم أنشأه المستخدم (`sec_<uid>`).

`render()` هو الموزّع الوحيد: يضبط الترويسة (عنوان + سهم رجوع + ترس) ثم
ينادي دالة رسم الصفحة.

**زر الرجوع في الجهاز** يُسلَّم للواجهة أولًا:

```java
webView.evaluateJavascript("… window.onAndroidBack() …", handled -> {
    if (!"true".equals(handled)) { /* اخرج من التطبيق */ }
});
```

و`onAndroidBack()` في JS: يغلق المودال → يرجع صفحة → يعيد `false` فيخرج.

## ٥أ. الأقسام والحقول الإضافية

`KINDS` ليست ثابتة: تُبنى في `applyData` من `DB.sections`، فكل ما يدور
عليها (السلة، المجموعات، التصنيفات، الحقول المرسلة، الرئيسية، النسخة
الاحتياطية) يشمل أقسام المستخدم بلا سطر إضافي.

```
ensureSections()   يضمن الأربعة الأصلية، يكتبها في القاعدة، ويحدّث KINDS
kindLbl(kind)      الاسم والأيقونة وألفاظ العدّ
secOf / isBuiltin  استعلام بسيط عن القسم
renderCustomSection(kind)  عارض عام لأي قسم أنشأه المستخدم
fieldsOf(kind) / extraFields(pfx,kind,o) / readExtra(pfx,kind)
oneExtra(pfx,f,val)      حقل واحد — يُستعمل للرسم وللحقن اللاحق
addFieldPanel + fldInline  إضافة حقل من داخل النموذج نفسه
```

**ألفاظ العدّ:** القسم الأصلي يحتفظ بألفاظه («٣ تحاليل») ما دام اسمه لم
يتغيّر؛ فإن سمّاه المستخدم باسم آخر رجعنا لألفاظ محايدة («٣ عناصر»). اشتقاق
جمع عربي صحيح من اسم كيفما كان غير ممكن، و«٣ وصفات» تحت اسم «الخلطات»
خطأ بيّن.

**إضافة حقل وأنت داخل النموذج:** اللوحة تُدرَج في الصفحة لا في مودال ثانٍ،
و`fldInline` **تحقن** الحقل الجديد في `#<pfx>-xf` بدل إعادة رسم النموذج —
فلا يضيع شيء ممّا أدخله المستخدم. تفريغ اللوحة يقع خارج `try` الحقن: الحقل
أُنشئ فعلًا، فتفريغها صحيح حتى لو تعذّر الحقن.

**قيم الحقول الإضافية** في `extra` (JSON) على صفّ العنصر، ومفتاح الحقل
يُولَّد مرّة ولا يتغيّر بإعادة التسمية. في «الحقول المرسلة» تظهر بمفتاح
مسبوق بـ`x:` يقرؤه `outValue`، وتُرسَم على بطاقة العنصر عبر `extraRow`.

**الحقل الجديد يُدرَج في `DB.out[kind]` لحظة إنشائه.** من عرّف حقلًا يريده
أن يظهر؛ ولو تُرك بلا إدراج لبقي ما يكتبه فيه غائبًا عن الطباعة والصورة
بلا سبب ظاهر — وهذا ما حدث فعلًا. الاختيار يبقى بيده بعدها من الإعدادات.

`backfillFieldOut()` تعالج الحقول التي عُرِّفت **قبل** ذلك: تُدرجها مرّةً
واحدة تحرسها العلامة `fields_out_done` في الإعدادات، فيبقى أي إلغاء تأشير
لاحق ثابتًا ولا تعيده الترقية في الإقلاع التالي.

> **مزلق:** `ensureSections` تكتب الصفّ في القاعدة فور استحداثه لا عند أول
> تعديل. `setSectionOrder` تُحدّث صفوفًا موجودة فقط، فلولا ذلك ضاع ترتيبٌ
> يغيّره المستخدم قبل أن يكون قد سمّى قسمًا واحدًا.

### قسمٌ مزروع: دليل العناوين

`seedDirectory()` تزرع «📇 دليل العناوين» بمعرّفٍ ثابت `sec_dir`: صفّ قسم
`builtin: 0`، وتصنيفاته الأربعة من `DIR_CATS`، وحقوله الخمسة من
`DIR_FIELDS` مُدرَجةً كلها في `DB.out[DIR_KIND]`. **لا جدول جديد ولا سطر
Java:** هو قسمٌ مستخدمٍ عاديّ يسكن `items` كغيره، فيرث السلّة والمجموعات
والترتيب والمعاينة والطباعة مجّانًا.

تحرسها علامة `dir_seeded` في الإعدادات لا وجودُ القسم — فمن حذفه لا تُعيده
ترقيةٌ لاحقة. وهذا هو الفرق عن `ensureSections`: تلك تستحدث ما يجب أن يكون
دائمًا، وهذه تقترح مرّةً وتقبل الرفض.

> **مزلق وقع فعلًا:** `seedDirectory()` قبل `seedCats()` تُسكِت تصنيفات
> الأقسام الأصلية إلى الأبد — شرط `seedCats` هو «لا تصنيف بعد»، وتصنيفات
> الدليل تكفي لنقضه. الترتيب في `boot()` مقصود: `seedCats()` ثم
> `seedDirectory()`.

`backfillDirGeo()` تُلحِق حقل الموقع بمن نال الدليل قبل وجوده — بعلامةٍ
مستقلّة `dir_geo` لا بـ`dir_seeded`. الفرق جوهري: من حذف حقل الموقع لا
يُفرَض عليه ثانيةً، ومن حذف الدليل كلّه لا يُبعَث له حقلٌ في قسمٍ غير
موجود (الشرط `secOf(DIR_KIND)`). وأي حقلٍ يُضاف لاحقًا يحتاج علامته هو —
لا تُعاد صياغة `dir_seeded` رقمَ إصدار.

### 📍 نوع الحقل `geo`

الأنواع في `FLD_TYPES` — مصدرٌ واحد تقرؤه `fldFormBody` (صفحة الحقول)
و`addFieldPanel` (داخل نموذج العنصر) معًا، فلا يُضاف نوعٌ في إحداهما
ويغيب عن الأخرى. `geoLink(v)` هي كل المنطق: إحداثيات ضمن المدى تصير
`https://maps.google.com/?q=…`، ورابط `http(s)`/`geo:` يمرّ كما هو، وما
عداهما يعود `''` — **لا نخترع موقعًا**، فرابطٌ إلى مكانٍ خطأ أسوأ من لا
رابط.

ثلاث نقاط تمسّ الإخراج:

- `outDefs` صارت تُعيد ثلاثيّات `[key, label, type]` — النوع يحتاجه بناء
  السطر المرسَل. الترتيب والعين لا يقرآن إلا `f[0]`، فلا يتأثّران.
- `outLines` تستبدل قيمة حقل `geo` برابطها وتضع `line.url`. فالإحداثيات
  تُحفَظ كما كتبها المستخدم، ويخرج الرابط وحده — «24.7, 46.6» لا تفتح
  شيئًا في واتساب.
- `itemsHtml` ترسم `line.url` وصلةً `<a class="rx-u">` بدل `textHtml`،
  فتُضغَط في الـPDF. والصورة ترسم النصّ نفسه (الرابط) لأن اللوحة لا
  تعرف الوصلات.

> **مزلق وقع فعلًا:** الوصلة على بطاقة العنصر داخل `<div class="grow"
> onclick="…">` — البطاقة نفسها تستمع للضغط (تفتح التعديل أو تؤشّر).
> `return false` يمنع التنقّل ولا يمنع التصعيد، فكان فتحُ الخريطة يفتح
> خلفها نموذج التعديل. `geoTap(event, url)` توقف الاثنين.

> **مزلق ثانٍ كشفه هذا العمل:** `fldPickType` كانت تكتب في `$('ff-type')`
> دائمًا — معرّفٌ لا وجود له داخل نموذج العنصر، فكل حقلٍ يُضاف من هناك
> يخرج «سطرًا واحدًا» مهما اخترت. الآن تبحث عن الحقل المخفيّ **بجوار
> الأزرار** (`btn.parentNode.parentNode`) وتسقط لـ`ff-type` عند التعذّر.

### 🔄 التحديث

`openExternal(url)` في `MainActivity` هي المنفذ الوحيد للخارج: نيّة
`ACTION_VIEW` بمخططات ثلاثة فقط (`http`/`https`/`geo`). هذا **لا** يحتاج
صلاحية إنترنت ولا يمنحها: نسلّم العنوان للنظام، والاتصال — إن وقع — يقع
في المتصفّح أو الخرائط بصلاحياتهما.

`updNow()` تفتح رابط الحزمة وتسجّل `upd_at`، و`updBanner()` تضع الشريط
على الرئيسية، و`updLater()` تؤجّل أسبوعًا عبر `upd_snooze` — لا تُسكِت
إلى الأبد، وإلّا كان التذكير زرَّ «لا تذكّرني».

**الفحص (٥٫٢):** `checkUpdate()` في جافا تجلب `dist/version.json`
(`{versionCode, versionName, notes}`) على خيطٍ منفصل، ثم تنادي
`window.onUpdateInfo(json)`. القرار رقمٌ مقابل رقم: `updNewer()` تقارن
`DB.updLatest.code` بـ`appVersionCode()` — لا تخمين من اسم الإصدار.

> **ارفع `dist/version.json` مع كل إصدار**، وإلّا لم يُخطَر أحد. هو
> الثالث في قائمة «ما يُرفَع»: `versionCode`، `versionName`، وهذا الملف.
> و`HEAD` في العنوان يعني الفرع الافتراضي للمستودع.

ثلاث نقاط في التصميم تستحقّ البقاء:

- **عنوانٌ ثابت في جافا** لا يأتي من الواجهة: لا شيء في JS يستطيع توجيه
  الاتصال إلى غيره. والمضيف يُتحقَّق منه *بعد* التحويل
  (`c.getURL().getHost()` مقابل `UPDATE_HOSTS`) لا قبله.
- **الوقت المسجَّل وقتُ المحاولة** (`upd_tried`) لا وقت الجواب: طلبٌ
  قُتِلت العملية وهو معلّق كان سيجعل كل فتحةٍ تطلب من جديد. والمعروض
  للمستخدم يبقى `upd_checked` — لا نقول «فُحِص» لشيء لم يصل.
- **كل فشلٍ صامت.** الفحص خدمةٌ إضافية؛ من لا شبكة عنده يجب ألّا يرى
  شيئًا. ولذلك يبقى تذكير `UPD_DAYS` الاحتياطي: من أطفأ الفحص أو تعذّر
  عليه ما زال يُذكَّر كل شهر.

> **مزلق:** الواجهة صار لها جارٌ يملك الشبكة. لذلك `WebViewClient` يرفض
> كل ما ليس `file://` — من غيره لصار أي رابطٍ يُقحَم في الأصول يومًا
> بابًا مفتوحًا، وكان القيد قبل ٥٫٢ محروسًا بغياب الصلاحية وحده.

## ٥ج. تسهيل الإضافة

إدخال عشرة عناصر كان يعني فتح النموذج وإغلاقه عشر مرات وإعادة اختيار
التصنيف في كل مرة:

```
mft(saveFn, id)        ذيل النموذج — «حفظ ومتابعة» عند الإضافة فقط
afterSave(kind, again, id)  يغلق، أو يفتح نموذجًا جديدًا جاهزًا للتالي
LAST_CAT[kind]         آخر تصنيف استُعمل — يُقترح في النموذج التالي
newItem(kind)          قيم البداية: نسخة DUP، أو LAST_CAT
dupItem(kind, id)      «⧉ تكرار» — نسخة بلا معرّف تُعدَّل ثم تُحفَظ
moreBlock(inner)       طيّ الحقول الأقل استعمالًا (العمود الرابع في *_FLD)
noHit / addNamed       بحثٌ بلا نتيجة يضيف بالاسم المكتوب مباشرةً
```

الحقول المطويّة تبقى في الـDOM، فقراءتها عند الحفظ لا تختلف — لكن أي
اختبار متصفّح يملؤها يحتاج فتح الطيّة أولًا.

## ٥ب. التصنيفات

التصنيف كيان مستقل في جدول `cats` لا نصّ داخل العنصر (التفصيل في
[`DATABASE.md`](DATABASE.md#cats--التصنيفات-كيان-مستقل)). في الواجهة:

```
catNames(kind)      أسماء القسم بالترتيب + أي اسم في العناصر لم يُسجَّل بعد
catEnsure(kind,n)   يسجّل التصنيف إن غاب — يُنادى عند حفظ عنصر وعند الاستيراد
catField(pfx,kind)  شرائح الاختيار داخل النموذج + «➕ تصنيف جديد» بلا مغادرته
groupBy(list,kind)  يجمع عناصر القسم في تصنيفاتها بترتيب المستخدم
renderCatsPage(k)   صفحة الإدارة: إنشاء/تسمية/ترتيب/حذف
```

`catNames` تضيف الأسماء اليتيمة (مكتوبة في عنصر ولم تُسجَّل — نسخة قديمة أو
استيراد) حتى لا يختفي تصنيف من القسم لمجرّد غيابه عن الجدول؛ صفحة الإدارة
تعرضها بزرّ «تسجيل».

**الزرع المبدئي يأتي من `library.js` نفسها** (`seedList`) لا من قائمة
موازية: قائمة مكتوبة يدويًا كانت ستختلف بحرف — «مسكّنات» و«مسكنات» — فيظهر
تصنيفان متطابقان معنى أول مرة يستورد فيها المستخدم من المكتبة. الزرع مرّة
واحدة يحرسها الإعداد `cats_seeded`.

## ٥د. تسهيل العرض والإرسال

```
accBlock(title, inner, open, pick)  «☑️ تحديد الكل» في رأس المجموعة
pickCat / pickFlag / toggleIds      تحديد تصنيف كامل أو رفعه عنه
PV_TAB 'list' → pvListHtml          تأشير وترتيب لهذا الإرسال وحده
pvOn() = PV.ids − PV.off          المؤشَّر وحده يُطبع ويُرسل ويُسجَّل
printCss(scope, dense)              مقاسان: عادي ومضغوط (DB.dense)
FMTS + DB.fmt                       الصيغة المفضّلة تتصدّر شريط الإرسال
PV.who + docBody(…, who) + outName  اسم المريض في الورقة واسم الملف
logSent / renderSentPage / sentOpen سجل آخر عشرة إرسالات
```

**تأشيرٌ لا حذف:** `PV.ids` قائمة المصدر كاملةً، و`PV.off` مجموعة
المستثنى منها لهذا الإرسال، و`pvOn()` ما بينهما — وهي وحدها ما يصل الورقة
والصورة والنسخ والسجل.

> **لماذا:** الطريقة العملية التي يحتاجها الطبيب هي مجموعة واحدة **شاملة**
> تصلح للغالب، ثم لكل مريض يؤشّر ما يرسله منها. الحذف كان يُلزمه بإزالة
> خمسة عشر عنصرًا ليرسل خمسة، ثم بإعادة بنائها للمريض التالي. التأشير
> يجعلها خمس لمسات، والمجموعة تبقى كما هي للمريض الذي يليه.

ولا شيء من ذلك يمسّ المصدر: `pvPick`/`pvAll`/`pvMove` تعمل على `PV` وحده،
فلا تتغيّر السلة ولا المجموعة المحفوظة. المعاينة نافذة على ما يخرج الآن لا
محرّر بيانات — والهامش في الواجهة يقول ذلك صراحةً.

**وضعان لا وضعٌ واحد مُشوَّش:** التطبيق يخدم عملين مختلفين — **بناء
الدليل** (إضافة وتعديل وتصنيف) و**إرسال قائمة لمريض** (تأشير وعرض وإرسال)
— وكانا مختلطين في شاشة واحدة: مربع تأشير وقلم وتكرار وسلة ونجمة في كل
بطاقة، وشريطٌ فيه أربعة أزرار مختلفة الغرض. بلاغ المستخدم بنصّه: «ما هو
واضح وين الإدخال ووين العرض والإرسال».

`mode()` يُرجع `send` أو `edit`، و`DB.mode` يُحفَظ في الإعدادات فلا يُعاد
اختياره في كل فتح. و`modeBar()` يتصدّر كل قسم **والرئيسية**: يُعرَف أين
أنت قبل أن تضغط شيئًا.

| | وضع 📤 الإرسال | وضع 📝 الإدخال |
|---|---|---|
| البطاقة | مربع تأشير واسم، والصفّ كلّه يؤشّر | ✏️ ⧉ 🗑️، بلا مربع تأشير |
| الشريط | 📁 المجموعات · ☰ القائمة | ➕ إضافة عنصر |
| تحته | شريط السلة عند التأشير | 🏷️ التصنيفات · 🧩 الحقول · 📚 المكتبة |
| رأس التصنيف | ☑️ تحديد الكل | — (فعلُ إرسال) |
| بحثٌ بلا نتيجة | «انتقل لوضع الإدخال لإضافته» | «أضِفه بهذا الاسم» |

خمسة أقسام (أربعة أصلية وما يُنشئه المستخدم) تمرّ كلّها من دالّتين:
`sectionBar(kind, q, placeholder, addCall)` و`itemCard(kind, o, body,
editCall, delCall)` — فلا يفترق قسمٌ عن آخر، ولا يُنسى وضعٌ في أحدها.

**البحث لا يهدم حقله:** `oninput` كان ينادي `render()` فيُعاد بناء
`#page` كاملةً مع كل حرف — ويُهدَم `#srch` نفسه ومعه التركيز، فلا يُكتب
فيه **إلا حرفٌ واحد**. الآن الشريط يُرسَم مرّة، والقائمة في `#sec-list`
وحدها تُحدَّث: `SEC_LIST[kind](q)` تبني القائمة، و`secSearch(kind)` تضعها.
الأقسام الخمسة كلّها تمرّ من هذا النمط.

> هذا مزلق عام: أي حقلٍ يُعيد رسم حاويته عند `input` يفقد تركيزه. المكتبة
> كانت تتجنّبه منذ البداية (`#lib-list`)، والأقسام لم تكن.

**أسماء الحقول اختيارية ومطفأة:** «متطلبات التحليل: صيام ٨ ساعات» يقرأها
المريض أثقل من «صيام ٨ ساعات». `DB.showLabels` (0 افتراضيًّا) يحكم ظهور
اسم الحقل في الورقة (`itemsHtml`) وفي الصورة والنصّ المنسوخ (`lineText`)
وفي النصّ (`listText`) — أربعة مخارج من مفتاحٍ واحد.

**الاسم والتاريخ طرفان لا ملتصقان:** `.sub` صار `flex` بـ`space-between`،
الاسم في `.who` والتاريخ في `.when`. واللوحة تفعلها بـ`textAlign` يمينًا
ثم يسارًا على السطر نفسه.

> **مزلق أصلحناه معها:** `pvWho` كانت تكتب `sub.textContent` — نصًّا خامًا
> يطمس الخانتين فيلتصق الاسم بالتاريخ من جديد. صارت تكتب في `.who` وحدها.

**الاسم يصل الصورة كما يصل الورقة:** `buildCanvas(…, pics, who)` يتلقّى
الاسم **مستقلًّا** عن العنوان. وكان مدموجًا في نصّ العنوان، فلمّا أُطفئ
العنوان سقط الاسم معه — ويظهر في الـPDF ولا يظهر في الصورة. له اختبار
يرصد ما يُرسَم على اللوحة فعلًا.

**عنوان الورقة اختياري ومطفأ افتراضيًّا:** «قائمة تحاليل» عنوانٌ يولّده
التطبيق لا المستخدم، ولا يضيف للمريض شيئًا. `DB.showTitle` (0 افتراضيًّا)
يحكم ظهوره في الورقة والصورة والنصّ المنسوخ معًا؛ ويبقى العنوان مستعمَلًا
في **اسم الملف** وفي سجل الإرسالات. ومن أراده كتبه بنفسه في حقل الاسم.
وبلا عنوان يصعد سطر الاسم والتاريخ ليملأ مكانه (`.sub.solo` في الورقة،
وإزاحة `y` في اللوحة).

**خلفية سطرٍ وسطر:** `.rx-item:nth-child(even)` — العين تتبع الصفّ بلا أن
تزيغ، وهو أهمّ ما في قائمةٍ طويلة. واللوحة كانت تفعلها أصلًا، فتطابقتا.

**ترتيب الحقول المرسلة:** ترتيب أسطر الورقة كان ترتيب الكود، فلا يملك
المستخدم تقديم «المتطلبات» على «الهدف». `DB.outOrder[kind]` قائمة مفاتيح
تُحفَظ في `ord_<kind>`، و`applyOutOrder` تطبّقها على `outDefs`: ما في
القائمة يتقدّم بترتيبه، وما ليس فيها — حقلٌ أُضيف بعدها — **يلحق في موضعه
الأصلي** فلا يختفي ولا يقفز إلى الصدارة. و`outLines` تقرأ من `outDefs`
فالورقة والصورة والنصّ المنسوخ تتبع تلقائيًا.

وصفحة الحقول صارت **قائمةً واحدة** بكل حقول الإرسال — الأصلية والمضافة
معًا بترتيبها على الورقة — لكل سطر زرّ ظهورٍ وسهما ترتيبٍ يحرّكانه بين
**كل** الحقول لا بين أقرانه، و✏️🗑️ للمضاف وحده.

**القائمة الجانبية: كل قسم يفتح على أعماله:** `drawerSection(k)` يجعل كل
قسمٍ `<details>` تحته أربعة مداخل مسمّاة — 📝 إضافة وتعديل (ومعها 📚
المكتبة حيث توجد)، 📤 عرض وإرسال، ↕️ ترتيب العناصر، 🖨️ الحقول المرسلة
وترتيبها. و`dwGo(kind, mode)` يضبط الوضع قبل الدخول، فيرى المستخدم شكل
الإرسال وحده أو أدوات الإدخال وحدها — لا خليطًا منهما.

**القائمة كاملة أو لا تكون:** «الحقول المرسلة» كانت تُسقِط حقلين من كل
قسم — **الاسم** (لأنه يظهر دائمًا) و**الصورة** (لأنها كانت تُطبع بلا خيار
أصلًا). فتبدو القائمة ناقصةً ويُستنتَج منها أنّ ثمّة حقولًا لا تُرسَل.

- **الصورة** صارت حقلًا كغيره: `['img','الصورة']` في `OUT_ALL` الأربعة وفي
  قاعدة الأقسام المُنشأة، و`rowsFor` لا تُخرجها إلا إن كانت مؤشَّرة.
  و`backfillImgOut` تؤشّرها **مرّةً واحدة** لمن كان يستعملها قبل ذلك
  (بعلامة `img_out_done`) وإلّا اختفت صوره فجأةً؛ ومن أخفاها بعدها تبقى
  مخفيّة. ومُضافة إلى `OUT_DEF` فالتثبيت الجديد يُرسلها كما كان دائمًا.
- **الاسم** يُذكَر صفًّا مقفلًا (🔒 `nameFieldLabel(kind)`) في الإعدادات
  وفي صفحة الحقول: يظهر دائمًا ولا يُلغى، لكنّه يُرى — فلا تبدو القائمة
  ناقصة ولا يُظنّ أنّه غير مُرسَل.

ويحرس ذلك اختبارٌ يقارن **أعمدة كل قسم كما تُحفَظ فعلًا** بما تعرضه
`outDefs`: كل عمودٍ له سطر، ولا سطر زائد.

**صفحة الحقول تحكم الترتيب والظهور معًا:** كان ظهور الحقل في العرض
والإرسال يُضبَط في الإعدادات، وترتيبه في صفحة الحقول، وحقول القسم الأصلية
في موضعٍ ثالث — ثلاثة أماكن لقرارٍ واحد. الآن `renderFieldsPage` يسرد
**كل** ما يخرج من القسم: الحقول المضافة (بـ▲▼ و✏️ و🗑️) ثم الأصلية، ولكلٍّ
زرّ `outEyeBtn` (👁️/🚫) يكتب في `DB.out[kind]` عبر `toggleOut`. حالة الزرّ
تُقرأ من شكله لا من ذاكرة المستخدم.

**`dangerBox` بدل `confirmBox` في كل ما لا رجعة فيه:** «حذف هذا العنصر؟
[تأكيد]» لا يقول ماذا يُحذف ولا كم، ولا يفرّق بين حذف سطرٍ وحذف قسمٍ بكل
ما فيه. `dangerBox({title, lose[], keep, word, action, onYes})`:

| | |
|---|---|
| `lose` | يُعدّ المفقود صراحةً بأعداده — «٣ تصنيفات»، «مجموعة واحدة»، «إزالته من قائمتك المحدَّدة» |
| `keep` | يذكر ما يبقى سالمًا، فلا يتردّد في حذفٍ صغير ظنًّا أنّه كبير |
| `action` | الزرّ يحمل اسم الفعل لا كلمة «تأكيد» |
| `word` | للأثقل وحده: الزرّ معطَّل حتى يُكتب الاسم بالضبط (`dzCheck`) |

الكلمة المكتوبة تُطلَب في ثلاثة مواضع: حذف قسم (اسم القسم)، واستعادة نسخة،
واستيراد ملف (كلمة «استبدال»). وما دونها صندوقٌ عادّ. و«مسح» التحديد كان
بلا تأكيدٍ إطلاقًا — صار له صندوقه، ومعه طمأنةٌ صريحة أنّ العناصر لا تُحذف.

**«نجحت الكتابة» ليست «تغيّر الصفّ»:** `UPDATE … WHERE id=?` على معرّفٍ
غير موجود يعيد صفر صفوف **بلا خطأ** — فتقول الطبقة «نجح» ويقول المستخدم
«لا يحفظ». لذلك `setItemOrder` في `DaliliDb` تكتب ثم **تقرأ وتقارن**
(`verifyOrder`) قبل أن تعيد `true`، والجسر يمرّر النتيجة، والواجهة تقولها
كما هي. مُثبَت على SQLite حقيقي: معرّف وهمي يمرّ بلا استثناء، والتحقّق
يكشفه.

**صفحة الترتيب (`sort:<kind>`):** زرٌّ صريح «↕️ ترتيب …» في شريط كل قسم
**وفي الوضعين** — الترتيب حاجةٌ قائمة سواء كنت تُدخِل أو تُرسِل. الصفحة لا
تفعل شيئًا إلا الترتيب: العناصر مفرودةً بتصنيفاتها، أسهمٌ كبيرة (`.ic.big`)
على كل عنصر وعلى رأس كل تصنيف، ولافتةٌ تقول إنّ كل حركة تُحفَظ ويُتحقَّق
منها، و«✅ تم» يعيد الكتابة ويؤكّدها قبل المغادرة.

**«💾 احفظ هذا الترتيب للقسم» في المعاينة (`pvKeepOrder`):** ترتيب المعاينة
مؤقّتٌ بطبعه وهذا مقصود، لكن من رتّب فيه ورضي الترتيب كان عليه أن يعيده في
القسم — فيظنّ أنّ الترتيب لا يُحفَظ. الزرّ يُعطي المؤشَّر مواضعه الأولى
ثم يُلحِق الباقي، فيصير ترتيب القسم.

**الترتيب يُضبَط حيث يُرى:** كان ترتيب العناصر غير ممكنٍ أصلًا، وترتيب
التصنيفات مخفيًّا في صفحةٍ أخرى لا يصلها إلا من يعرف مكانها. الآن في وضع
📝 الإدخال:

- **▲▼ على بطاقة كل عنصر** (`orderBtns` داخل `itemCard`, و`itemMove`):
  يتحرّك بين **جيرانه في تصنيفه** (`sibsOf`)، والتبديل يقع في القائمة
  الكاملة ثم يُكتب ترتيب القسم كلّه بـ`Store.setItemOrder` → عمود
  `sort_order` (`DaliliDb.setItemOrder`).
- **▲▼ في رأس كل تصنيف** (`catMoveBtns`, `catMoveNamed`): يتحرّك بين
  التصنيفات **الظاهرة** (`catsShown`) لا الجار الخام.

> **مزلقان حقيقيان هنا:** (١) التبديل مع جارٍ خام قد يقع مع تصنيفٍ فارغ لا
> يظهر في القسم — فلا يتغيّر شيء أمام المستخدم ويظنّ أنّ الترتيب لم يُحفَظ،
> وهو محفوظ لكنّه غير مرئي. (٢) اسمٌ مكتوبٌ داخل العناصر وحدها بلا صفّ في
> `cats` لا يُرتَّب أصلًا — يُسجَّل الآن عند أول تحريك، **وبترتيب الظهور لا
> بترتيب النداء**، وإلا وُلِد الصفّان مقلوبين فجاء التبديل معكوسًا.

وكل تحريك يُحدِّث السلة فورًا (`orderOf`) فلا تتأخّر الورقة عن الشاشة.

**ترتيبٌ واحد في كل مكان:** ما يراه المستخدم في القسم هو ما يخرج في
الورقة. `displayOrder(kind)` تُخرج معرّفات القسم بترتيب عرضها — التصنيفات
كما رتّبها المستخدم، وداخل كلٍّ عناصره — و`orderOf(kind, ids)` ترتّب أي
مجموعة معرّفات عليه.

- **السلة** تُحفَظ مرتَّبةً لا بترتيب النقر (`toggleCart`, `toggleIds`):
  كان من يؤشّر من أسفل القائمة ثم من أعلاها تخرج ورقته معكوسةً عمّا أمامه.
- **المجموعة** تستقبل الدفعة الجديدة بترتيب العرض (`grpAddItems`,
  `groupLibAdd`) — وما فيها يبقى كما رتّبه هو بـ▲▼، فالإضافة تُلحِق ولا
  تُعيد الترتيب.
- **المعاينة** تبدأ من هذا الترتيب، و⬆️⬇️ فيها لهذا الإرسال وحده.
- **`pruneOrphans`** تعيد ترتيب السلال المحفوظة بترتيب النقر مرّةً واحدة
  عند أول إقلاع — بنفس شرطها: قراءةٌ نظيفة تمامًا.

فالورقة والصورة والنصّ المنسوخ والمجموعة كلّها تقرأ من ترتيبٍ واحد. وتحريك
تصنيف في صفحة التصنيفات يُعيد ترتيب كل ذلك معًا.

**اتجاه كل سطر من لغته لا من الصفحة:** الورقة عربية، فسطرٌ اسمه لاتيني كان
يُرسَم «Urea .1» — الرقم في الطرف الخطأ والنقطة قبله، لأن الأرقام وعلامات
الترقيم لا اتجاه لها فتأخذ اتجاه الفقرة.

- **الورقة:** `dir="auto"` على `.rx-name` وعلى كل `.rx-f` — المتصفّح يستنتج
  الاتجاه من أول حرفٍ ذي اتجاه. على السطر لا على الصندوق: سطور الحقول
  تبقى عربية (عناوينها عربية) مهما كانت لغة الاسم فوقها.
- **الرقم عنصر مستقل:** `outTitle` لم تعد تلصقه بالاسم؛ `rowsFor` تُخرج
  `n` و`title` منفصلين، و`.rx-name` صندوق `flex` فيه `.rx-n` بعرضٍ محجوز
  و`text-align:start` — فتصطفّ الأسماء تحت بعضها والرقم في الطرف الصحيح.
- **الصورة:** لا `dir=auto` في لوحة الرسم، فـ`dirOf(text)` تُرجع الاتجاه
  من أول حرفٍ ذي اتجاه، ويُرسَم السطر من `PAD` أو من `W - PAD` بحسبه.
- **النصّ المنسوخ:** محرف `LRM`/`RLM` غير مرئي قبل الرقم يثبّت ترتيب السطر
  في واتساب وغيره.

مقيسٌ آليًا: قائمة مختلطة من أحد عشر اسمًا، صفرٌ منها في الطرف الخطأ.

**اسم المريض يُحدَّث بالـDOM لا بإعادة الرسم:** `render()` يكتب `innerHTML`
من جديد فيفقد الحقل تركيزه وسط الكتابة؛ لذلك `pvWho` تحدّث سطر `.paper .sub`
وحده.

**السجل لقطة لا علاقة حيّة** (انظر [`DATABASE.md`](DATABASE.md)): عنصر
حُذف بعد إرساله يُستبعَد عند الاسترجاع مع إشعار، ولا يُفسد السجل.

## ٥هـ. مكتبة الصور والرموز داخل النصّ

```
DB.images[]              {id, code, name, data} — data URL
segsOf(text)             يقسّم النصّ: مقاطع نصّ ومقاطع {رموز} معروفة
textHtml(v)              للمخارج التي تفهم HTML — الرمز يصير <img>
plainText(v)             للنصّ المنسوخ — الرمز يصير [صورة: الاسم]
imgField / imgSel        اختيار صورة العنصر من المكتبة
imgsUsed + loadImgs      تحميل الصور قبل رسم اللوحة
```

**لماذا data URL لا ملف؟** عارض الطباعة WebView منفصل ولا يرى ملفات
التطبيق، ولوحة الصورة تحتاج البيانات في نفس اللحظة، والنسخة الاحتياطية
تحملها معها. الواجهة تصغّر الصورة قبل الحفظ فلا تنتفخ القاعدة.

**الرمز لا يتغيّر بعد الإنشاء** — تغييره يكسر كل نصّ يشير إليه. الاسم وحده
قابل للتعديل، ورمز غير معروف يبقى نصًّا كما كتبه المستخدم فلا نخترع صورة.

**اللوحة صارت غير متزامنة:** `drawImage` تحتاج صورة محمَّلة، وقياس ارتفاع
الصفّ يحتاج أبعادها — فـ`shareList` و`pvImgFill` تحمّلان أولًا ثم تبنيان.
لذلك تبويب الصورة يعرض «⏳ يجري التجهيز» لحظةً ثم يحقن اللوحة.

## ٦. الطباعة والمشاركة

> **`window.open` لا يعمل داخل WebView إطلاقًا.** هذا كان سبب رسالة «اسمح
> بالنوافذ المنبثقة» وصمت زر الطباعة في الإصدارات الأولى. لا تعتمد عليها.

### الطباعة

```
printCss(scope) + docBody(title, body)         ← مصدر واحد للتنسيق والمحتوى
   ├─ printDoc(title, body)                    ← صفحة HTML كاملة
   │    ├─ printList → AndroidBridge.printHtml ← مربع الطباعة (PrintManager)
   │    └─ pdfList   → AndroidBridge.sharePdf  ← ملف PDF ثم قائمة الإرسال
   └─ renderPreview() → <div class="paper">    ← المعاينة داخل التطبيق
```

**إرسال PDF مباشرةً** (`sharePdf`) يستخدم نفس محرّك الطباعة لكن بدل تسليمه
لـ`PrintManager` يستدعي `onLayout` ثم `onWrite` بنفسه ويكتب الناتج ملفًّا،
فيخرج PDF جاهزًا للإرسال بلا أي واجهة نظام وسيطة.

`AndroidBridge.printHtml` ينشئ WebView مؤقتًا، ينتظر `onPageFinished`، ثم
يمرّر `createPrintDocumentAdapter` إلى `PrintManager`. **يجب** الاحتفاظ
بمرجع للعارض (`printView`) وإلا جُمِع قبل انتهاء توليد الـPDF.

ورقة الطباعة في `printCss('')`: مقاسات بالنقاط، `@page { size: A4 }`، وأسطر
متقاربة، و`page-break-inside: avoid` لكل عنصر.

### المعاينة قبل الإرسال

`printCss(scope)` هي السبب في أن المعاينة **هي** المستند لا نسخة منه: عند
تمرير `'.paper'` تُسبَق كل قاعدة بالمُحدِّد فتُحصَر داخل بطاقة المعاينة ولا
تسرّب إلى واجهة التطبيق، ويُحذف `@page` لأنه بلا معنى داخل الصفحة. الحقن
مرّة واحدة عبر `ensurePreviewCss()` (يحرسه `PV_CSS`).

```
openPreview(kind, ids, title, imgTitle)   ← يملأ PV ثم goPage('pv')
   renderPreview()
      ├─ PV_TAB 'paper' → docBody(...)    ← نفس جسم المستند المُرسَل
      └─ PV_TAB 'img'   → buildCanvas(...).toDataURL()
   pvSend('pdf'|'img'|'print'|'copy')     ← pdfList / shareList / printList / copyList
```

مداخلها ثلاثة: `previewCart(kind)` من شريط السلة، و`groupEditPreview()` من
محرّر المجموعة، و`groupPreview(id)` من قائمة المجموعات. أي قائمة فارغة
تُصفّر `PV` حتى لا يُرسَل تحديد قديم بالخطأ.

> **مزلق:** `goBack()` كان يصفّر `GRP` دائمًا. بعد إضافة المعاينة صار
> الرجوع منها إلى المحرّر يمرّ بنفس الدالة، فكان يُسقط مسوّدة المجموعة
> بصمت. الآن تُصفَّر فقط عند مغادرة صفحة `grp:` نفسها.

### المشاركة كصورة

`buildCanvas(kind, ids, title)` يرسم القائمة على `<canvas>`:

1. يقيس النص أولًا (`wrapText`) لحساب الارتفاع المطلوب
2. يضبط أبعاد اللوحة ثم يرسم (تغيير الأبعاد يصفّر سياق الرسم — أعِد ضبط
   الخطوط بعده)
3. `toDataURL` → `AndroidBridge.shareImageBase64` → `FileProvider` →
   `ACTION_SEND`

**لماذا صورة لا PDF؟** رسم النص العربي في المتصفح يضبط الاتجاه والتشكيل
تلقائيًا وبدقة، بخلاف توليد PDF يدويًا الذي يحتاج تضمين خطوط وقد يُخرج
حروفًا مفكّكة.

### النسخ كنص

`copyList(kind, ids, title)` يبني نصًّا عاديًا (ترويسة اختيارية + عنوان
وتاريخ + عناصر بنقاط) ويمرّره إلى `AndroidBridge.copyText` الذي يضعه في
حافظة النظام. في المتصفح يستخدم `navigator.clipboard`.

### حقول النص الطويل

`taField(id, label, value, placeholder)` تبني الحقل كاملًا: تسمية + شريط
إدراج (نقطة / ترقيم / سطر جديد) + `<textarea>` يتمدّد مع المحتوى عبر
`grow()`. و`taKey()` تجعل Enter يُكمل القائمة تلقائيًا، وعلى علامة فارغة
يُنهيها. `growAll()` تُستدعى بعد `openModal` ليظهر النص المحفوظ كاملًا.

الأسطر الجديدة تصل إلى المخرجات الثلاثة: `white-space: pre-wrap` في ورقة
الطباعة وبطاقات القوائم، و`wrapBlock()` في الصورة، وإزاحة أسطر التكملة في
النص المنسوخ.

### ترويسة الطباعة

`DB.header` = `{name, title, contact}` — كلها **اختيارية وفارغة افتراضيًا**.
`headerHtml()` يعيد نصًّا فارغًا ما لم يُملأ سطر منها، فلا تظهر كتلة الترويسة
في الورقة إطلاقًا. تُحفظ في `settings` بالمفاتيح `hdr_*`.

### النسخ الاحتياطي التلقائي

`autoBackup(force)` تُستدعى عند كل إقلاع: تكتب نسخة إن مرّ يوم على آخر واحدة
وكانت هناك بيانات. شرط «وكانت هناك بيانات» يسري حتى مع `force`: نسخةٌ فارغة
تُزيح أقدم النسخ الخمس، فتضيع آخر نسخةٍ صالحة في اللحظة التي يُحتاج فيها
إليها. وتُؤخذ نسخة أمانٍ قبل كل عملٍ يستبدل أو يبتلع بيانات: استعادةُ نسخة،
استيرادُ ملف، وحذفُ قسمٍ كامل (أكثر حذفٍ كلفةً في التطبيق —
يأخذ عناصره وتصنيفاته ومجموعاته معه).

`BackupStore.java` يتولّى الموضع: مجلد التطبيق الخاص
افتراضيًا، أو مجلدًا يختاره المستخدم عبر `ACTION_OPEN_DOCUMENT_TREE` مع
`takePersistableUriPermission` فيبقى بعد إعادة التشغيل. التفاصيل في
[`DATABASE.md §١٠`](DATABASE.md).

### الحقول المرسلة

`DB.out[kind]` مصفوفة أسماء حقول. `outLines()` تمرّ على **تعريف** الحقول
(`OUT_MEDS` / `OUT_LABS` / `OUT_RECIPES`) وتصفّي بالمختار — فيبقى الترتيب
ثابتًا لا يتبع ترتيب نقر المستخدم. الاسم يظهر دائمًا، ورمز التحليل والاسم
العلمي يُدمجان في سطر الاسم إن اختيرا.

## ٧. المجموعات المسمّاة

المحرّر **يكتب فور كل تعديل**. `GRP` مجرّد إشارة للمجموعة المفتوحة
(`{id, kind, name}`) يحتاجها المنتقي والمعاينة، لا مخزن حالة:

```js
function grpEdit(fn) {
  var g = findGroup(GRP.id); if (!g) return;
  fn(g);                       // عدّل الكائن الحيّ في DB.groups
  GRP.name = g.name;
  Store.saveGroup(g);          // اكتبه
  render();
}
```

`groupPickAdd` و`groupRemove` و`groupItemMove` و`groupRenameSave` كلّها تمرّ
من هنا، فلا زرّ «حفظ» ولا حالة `dirty` ولا سؤال عند الخروج.

> **كان** يعمل على مسوّدة تحتاج ضغط «حفظ»، خدمةً لـ«عدّل وأرسل بلا أن تمسّ
> الأصل». والنتيجة أنّ من يضيف عناصر ثم يخرج يجدها ضاعت — بلاغٌ وصل بنصّه:
> «ما يحفظ العناصر». وتلك الحاجة صار يخدمها تعديل القائمة داخل المعاينة
> نفسها (§٦)، وهو لا يمسّ المجموعة أصلًا، فلم يبقَ للمسوّدة مبرّر.

**الترتيب** في الموضعين يُحفَظ: `groupItemMove` يبدّل داخل `g.items` (وهو
ترتيب الورقة والرسالة)، و`groupMove` يبدّل داخل `DB.groups` كاملةً ثم
`Store.setGroupOrder(...)` — التبديل على القائمة الكاملة لا المرشّحة، فيثبت
الترتيب سواء رُتّب من صفحة قسمٍ واحد أو من الدرج الجامع.

### بطاقة المجموعة: ثلاثة إجراءات مكتوبة

`groupCard(g, i, n)` واحدة تخدم صفحة المجموعات والدرج معًا، وفيها
**➕ إضافة عنصر · 👁️ عرض · 📤 إرسال** مكتوبةً لا مرموزة (و«إرسال» معطّل
ما دامت المجموعة فارغة). كانت الإجراءات مخبّأة — الضغط على الاسم يرسل،
وقلمٌ صغير يحرّر، ولا سبيل لإضافة عنصر إلا بالدخول ثم البحث عن زر.

`groupAddTo(id)` تفتح المجموعة **ثم منتقيها** في خطوة واحدة من أي قائمة.

### المنتقي لا يكون طريقًا مسدودًا

منتقي العناصر كان يعرض «لا نتائج» ثم لا شيء. وثلاث حالات تصل إليه ولكلٍّ
مخرجها الآن، بلا مغادرة المودال:

| الحالة | المخرج |
|---|---|
| القسم فارغ أصلًا | «➕ أنشئ عنصرًا جديدًا وأضِفه» — `groupAddNew` يفتح نموذج القسم كاملًا |
| بحثٌ بلا نتيجة | «➕ أنشئه وأضِفه للمجموعة» — `groupAddNamed` بالاسم المكتوب |
| في الحالتين | «📚 أو اختر من المكتبة الجاهزة» — ينقل للتبويب أدناه |
| تعذّرت قراءة القسم | تحذير و🩺 فحص — **لا** دعوة للإضافة فوق بياناتٍ لم تُقرأ |

#### تبويب المكتبة الجاهزة

المنتقي تبويبان: **📋 عندي** و**📚 المكتبة الجاهزة** (`GP_TAB`). والثاني
يسرد `window.LIBRARY[kind]` كاملةً ببحثه (`libHay`)، وما يُختار منه
يُستورَد للقسم **ويدخل المجموعة** في خطوة واحدة (`groupLibAdd`).

قبله كان على من قسمُه فارغ أن يغادر المجموعة إلى الإعدادات ← المكتبة،
يستورد، يعود، ثم يبحث — أربع خطوات في ثلاث صفحات.

`libMineOf(kind, src)` تمنع الاستنساخ: ما استورده المستخدم من قبل يُضاف
للمجموعة **بمعرّفه هو** لا بنسخةٍ ثانية؛ والمطابقة بـ`libKey` نفسه الذي
تستعمله صفحة المكتبة. وما هو في المجموعة أصلًا يظهر باهتًا معطّلًا.

وتبويب المكتبة يخضع لحارس `kindFailed` كغيره: قسمٌ لم تُقرأ عناصره لا
يُستورَد فوقه شيء — وإلا صارت كل عناصره الموجودة نسخًا مكرّرة.

`groupAddNew` تلتقط ما يُستحدث عبر `GRP_CATCH`: تسجّل معرّفات القسم قبل
فتح النموذج، و`grpCatch(kind)` في `afterSave` تضيف الفرق إلى المجموعة ثم
تعيدك لصفحتها لا لصفحة القسم. و`grpAddItems` لا تكرّر معرّفًا موجودًا.

### الدرج الجانبي — القائمة الواحدة

`openDrawer()` / `closeDrawer()` على `#dw` و`#dw-bg` خارج `#app` (كالمودال،
فيظهر فوق أي صفحة). ثلاث مجموعات في قائمة واحدة:

1. **الأقسام** — كل `KINDS` بأيقونته وعنوانه وعدد عناصره (`drawerGo`)
2. **الأدوات** — سجل الإرسالات، مكتبة الصور، الإعدادات
3. **المجموعات المحفوظة** — والضغط على الصفّ **يرسل مباشرةً**
   (`drawerSend` → `groupPreview`): المجموعة تُحفَظ لتُرسَل، فليكن الإرسال هو
   الإجراء الأول لا الثالث

`onAndroidBack` يغلقه قبل أن يغادر الصفحة. وهو يُعاد رسمه عند كل فتح لأن
ترتيبه ومحتواه يتغيّران من داخله.

## ٧أ. الإشارات اليتيمة — «إمّا موجود أو غير موجود»

السلة والمجموعات وسجل الإرسالات تحفظ **معرّفات** لا عناصر. معرّفٌ بلا عنصر
كان يُرسم `(عنصر محذوف)`، فرأى المستخدم قائمةً من عشرة كلّها أشباح وسأل
بحقّ: «كيف عنصر محذوف؟ إمّا موجود أو غير موجود».

قاعدتان:

| | |
|---|---|
| **لا يُعرَض** | `liveIds(kind, ids)` ترشّح أي قائمة قبل عرضها. `openPreview` لا تفتح إلا على القائم، وترفض تمامًا إن لم يبقَ شيء؛ و`renderGroupPage` تعرض القائم وحده |
| **لا يُحفَظ** | `pruneOrphans()` عند الإقلاع تمسح المعرّفات اليتيمة من السلة والمجموعات وتكتب التنظيف |

### «فارغ» ليست «لم أستطع القراءة»

الحالتان تبدوان واحدة على الشاشة وهما نقيضان: الأولى لا شيء فيها، والثانية
فيها كل شيء ولا نراه. وصندوق «لا توجد تحاليل محفوظة» فوق جدولٍ عامر ليس
نقصًا في العرض — بل كذبةٌ تدفع المستخدم لإعادة الإدخال فوق بياناته. حصل
ذلك فعلًا: صفحة تصنيفات كلّها «فارغ» وجدولُ العناصر عامر.

`kindFailed(kind)` تسأل `Store.errors` إن كان جدول هذا القسم قد تعذّر،
و`emptyOrFailed(...)` تختار الصندوق الصادق. والتحذير يظهر في أربعة مواضع لا
واحد: صفحة القسم، صفحة تصنيفاته (حيث رآه المستخدم)، بطاقة الرئيسية، ولافتة
ثابتة أعلى الرئيسية — **لافتة لا إشعارًا عابرًا**: ما لا يُقرأ يجب أن يُرى
في كل فتح لا مرّةً واحدة بعد ثانية.

### 🩺 صفحة الفحص (`diag`)

`DaliliDb.diagnose()` تسأل SQLite مباشرةً: ما الجداول، وكم صفًّا في كلٍّ
منها (`SELECT COUNT(*)`)، وما أعمدته (`PRAGMA table_info`)، وهل تنجح
القراءة التي تستعملها الواجهة (`readItems`). الصفّ الذي فيه صفوفٌ ولا
تُقرأ يُعلَّم ⚠️ — وهذا هو السطر الذي يفصل الحالتين أعلاه.

الصفحة متاحة من الإعدادات، ومن شاشة الإنقاذ نفسها (حيث هي أنفع ما تكون)،
ومن كل تحذير. و«📋 نسخ التقرير» يخرج نصًّا فيه أسماء الجداول وأعدادها
وأعمدتها وأخطاؤها — **ولا شيء من بيانات المستخدم**، فيصلح للإرسال.

> **لماذا:** جولتان كاملتان من التخمين عن سبب اختفاء قسم ضاعتا لأنّ الفرق
> بين «الجدول فارغ» و«تعذّرت قراءته» لم يكن مرئيًا من الواجهة. هذه الصفحة
> تجعله مرئيًا في ضغطتين.

### قراءةٌ لا تسقط لأجل الترتيب

`str/num/lng` تتسامح مع عمودٍ ناقص، لكن `ORDER BY sort_order` جملةُ SQL:
عمودٌ ناقص فيها يرمي **قبل أن يصل صفٌّ واحد**، فيبدو الجدول فارغًا وهو
عامر. `rows(db, table, sel, args)` تجرّب المرتَّب ثم تسقط لغير المرتَّب —
ترتيبٌ غير مثالي خيرٌ من قسمٍ فارغ. تمرّ منها كل قراءات الجداول.

والشرط الحاكم في `pruneOrphans`: **لا تعمل إلا بعد قراءةٍ نظيفة تمامًا**
(`Store.ok && !Store.errors.length`). لو فشلت قراءة جدول العناصر وحده
لبدت كل الإشارات يتيمة، فيمسح التنظيفُ تحديدَ المستخدم ومجموعاته بناءً على
قراءةٍ خاطئة — وهو الخطأ نفسه الذي كلّفنا قسمًا ووصفات (§٦أ في
[`DATABASE.md`](DATABASE.md)). مغطّى باختبار صريح.

## ٨. المكتبة الجاهزة

`library.js` يعرّف `window.LIBRARY = { labs: [...], meds: [...] }` — بيانات
ثابتة مدمجة. الإضافة تنسخ العنصر وتعطيه `id` جديدًا فيصير ملك المستخدم
يعدّله كما يشاء.

- منع التكرار بمفتاح: `code|name` للتحاليل، `trade_name|scientific_name`
  للعلاجات (`libKey()`)
- الإضافة دفعة واحدة عبر `upsertMany` (معاملة واحدة)
- **حقل `dosage` فارغ عمدًا في كل علاجات المكتبة** — الجرعة تختلف بالحالة
  والعمر والوزن ووظائف الكلى والكبد. لا تملأه ببيانات عامة.

لإضافة عناصر: عدّل `library.js` مباشرةً بنفس شكل الكائنات. الاختبار
`كل عناصر المكتبة تحمل الحقول المطلوبة` سيرفض أي عنصر ناقص أو مكرّر أو
يحمل جرعة.

## ١٠. الاختبارات

```bash
node tools/test_store.js
```

١٦٨ اختبارًا، بلا أي حزم خارجية. الفكرة: تشغيل `app.js` **الحقيقي** داخل
`vm` مع DOM وهمي مبسّط وجسر `NativeDb` وهمي يحاكي دلالات `DaliliDb`
(جداول منفصلة، سلة مرتّبة، مجموعات).

يغطّي: CRUD للأقسام الثلاثة، البقاء بعد إعادة التشغيل، الترحيل من
`localStorage` (ولا يتكرر ولا يطمس)، رمز القفل، النسخ الاحتياطي، الحقول
المرسلة ومخرجات الطباعة، المكتبة وبحثها وسلامة بياناتها، التنقّل وزر
الرجوع، والمجموعات (تعديل/حفظ/رجوع بلا حفظ)، والمعاينة (التبويبان،
تطابق المعروض مع المُرسَل، ورفض القائمة الفارغة)، والتصنيفات (الإنشاء
والإسناد وإعادة التسمية والحذف والترتيب والزرع مرّة واحدة)، والأقسام (إنشاء قسم كامل، تسمية
الأصلي، الترتيب، الحذف بما يتبعه) والحقول الإضافية (التعريف والحفظ
والطباعة وثبات المفتاح عند إعادة التسمية)، و**تأمين البيانات**: قراءة فاشلة
لا تكتب حرفًا ولا تزرع، درع الكتابة، شاشة الإنقاذ والاستعادة منها، رفض
النسخة الفارغة، نسخة الأمان قبل حذف قسم، والعطب الجزئي الذي لا يُخفي
البقيّة ([`DATABASE.md §٦أ`](DATABASE.md)).

**ما لا يغطّيه:** كود جافا. لا `DaliliDb` ولا `PrintManager` ولا
`evaluateJavascript` يُختبر آليًا هنا — يُبنى ويُترجم فقط. أي تعديل في جافا
يحتاج تجربة على جهاز.

أضِف اختبارًا مع كل ميزة. النمط:

```js
run('وصف بالعربية', () => {
  const b = makeBridge(); const c = load(b); c.Store.load(); c.showApp();
  …
  eq(actual, expected, 'وصف قصير:');
});
```

## ١٢. إضافة قسم رابع — خطوة بخطوة

> طُبّقت هذه الخطوات فعلًا عند إضافة قسم **الأشعة والفحوصات** (`imaging`) —
> راجع الالتزام المقابل في تاريخ المستودع كمثال كامل.

مثال: «اللقاحات».

**قاعدة البيانات** (`DaliliDb.java`)
1. `KINDS` ← أضِف `"vaccines"`
2. عرّف `VACCINE_TEXT_COLS`
3. `textCols()` و`flagCol()` ← أضِف الفرع
4. `createVaccines(db)` ونادِها من `onCreate`
5. ارفع `DB_VERSION` وأضِف `if (oldVersion < N) createVaccines(db);`

**الواجهة** (`app.js`)
6. `KINDS` ← أضِف `'vaccines'`
7. `KIND_LBL` ← التسميات والأيقونة وصيغ العدد
8. `coll()` و`setColl()` ← أضِف الفرع
9. `OUT_VACCINES` + `OUT_DEF.vaccines` + `outDefs()`
10. `PAGES` ← عنوان الصفحة، و`render()` ← فرع الرسم
11. اكتب `vaccineRow` / `renderVaccines` / `vaccineForm` / `vaccineSave` /
    `vaccineDel` على نمط الوصفات
12. `outTitle()` ← فرع العنوان، و`cartTitle()` ← اسم القائمة
13. الإعدادات ← `outBlock('vaccines', …)` وزر الإضافة السريعة

**التوثيق والاختبار**
14. `docs/schema.sql` + `docs/DATABASE.md`
15. اختبارات في `tools/test_store.js` (والجسر الوهمي فيه يحتاج الجدول الجديد)
16. `node tools/test_store.js` ثم `./gradlew assembleRelease`

السلة والمجموعات والطباعة والمشاركة والنسخ الاحتياطي **تعمل تلقائيًا** —
كلها معمّمة على `KINDS`.
